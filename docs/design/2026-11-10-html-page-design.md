# 页面设计重构：模型用 HTML 设计页面，代码转成原生 PPT（2026-11-10）

状态：Jay 2026-11-10 批准。

标注说明：没有标注的内容是 Jay 说过或确认过的；标「Claude 的决定」的是 Claude 替 Jay 做的选择，Jay 可以推翻。

## 1. 为什么改

Jay 在找 AI 产品经理 / AI 应用方向的实习，ppt-agent 是简历上的项目。现在有两个问题：

1. **页面不够精美。** 同一需求下，Jay 的排序是 Claude Code > ppt-agent > Codex，而且 Jay 认为 Claude Code 那一版的精美度也只是一般。项目如果做不出比宿主模型更好看的页面，就失去了意义。
2. **100 页时重复明显。** 既有版式重复，也有内容重复（一次真实运行里「95%」出现在 8 页，13 页退化，表格占 17 页）。

### 根因判断（Claude 的判断，Jay 看过对比后没有反对）

- 现在是「模型从 29 种构图里选一个，再把内容填进去」。所有构图共用一套外观（深蓝、橙、矩形色块），页面的形状不随内容变化。继续加构图，结果还是模板感。上一轮计划（`visual-upgrade-plan.md`）已经写过「还是第三就停止打磨版式」。
- 每页只拿到 4 段左右的检索片段，各写各的，全稿没有贯穿的论证，所以页数多了就重复。
- Claude Code 好的地方：先读全文，再为每一页单独设计。

### 已做的验证

一次性试验（`data/spike-html2pptx/`，不进 Git，不是产品代码）：把 12 页手写 HTML 样张（三种视觉方向各 4 页）用浏览器量出每个元素的位置，转成原生 PPT 元素，再用 PowerPoint 导出对比。

- 位置、色块、圆角、渐变填充、光晕、渐变文字都还原了；163 个文本框、66 个形状，没有截图；没有溢出或重叠。
- 字体有偏差：试验用了苹方和宋体-简，PowerPoint 换了字形，粗宋体没有出来。
- 没有验证：原生图表、表格、图片、Windows 上的效果、WPS。

结论：这条路走得通，字体是最需要先解决的问题。

## 2. 目标

1. **页面精美度**：同一需求下，由不知道来源的人盲评，ppt-agent 排在 Claude Code 和 Codex 之前（验收方法见第 8 节）。
2. **三套主题**都可用：杂志编辑、深色科技、明亮现代（Jay 看过样张，三套都要）。
3. **100 页不重复**：版式和内容都有可量的指标（第 8 节）。
4. **保住现有卖点**：原生可编辑；每页标注出处页码；数字核对；可通过 MCP 调用、澄清需求、修订单页。
5. **简历上有新东西可写**：用数据说明「发现模板路线到头、判断根因、重构、验证」这条线，以及「生成后自己看图检查并返修」。

## 3. 不做的事

- 不加向量检索、新的输入格式、动画、演讲者视图等功能。
- 不继续给旧排版引擎加构图或骨架。
- 不追求在没有装 Office 的机器上显示完全一致。
- 不做 Keynote 兼容。WPS 只检查一次并记录结果，不作为验收门槛（Claude 的决定）。
- 不重做「图片转可编辑 PPT」功能，它保持现状。

## 4. 绝对不能出现的结果

即使其他都做到了，出现下面任何一条都算失败：

- 把整页或大块内容做成图片贴进 PPT。文字必须是文本框，图表必须是原生图表，表格必须是原生表格。
- 页面上出现没有经过核对的数字，或者出处页码丢失。
- 为了凑页数重复内容。
- README 或简历里写超出实测数据的结论（例如没有做盲评就写「优于 Claude Code」）。

## 5. 约束

- **模型与网关**：测试用的代理模型每秒约 35 个 token，网关约 125 秒断开。单次调用的输出要控制在约 3500 token 以内，所以一次调用只设计一页，页与页之间并发。
- **全流程只用 `gpt-5.6-terra`**（Jay 2026-11-10 决定）：内容步、设计步、看图步都用它，不引入第二个模型。
- **看图需要视觉模型**：`providers.py` 已有 `encode_image_for_vision`（图片重建功能在用）。看图检查用同一套接口。
- **字体**：Office 在 Windows 和 macOS 上都自带微软雅黑、等线、宋体、黑体、楷体、仿宋。现有代码就是因为这一点统一用微软雅黑。新主题也只能用这些字体，并且浏览器量尺寸时必须用同一份字体文件，否则换行位置会不一致。
- **提交习惯**：提交不加 Claude 署名，push 由 Jay 自己做。
- **协作方式**：Claude 负责计划和审核，执行由 Jay 和另一个 AI 完成，除非 Jay 明确要求 Claude 动手。
- **验收方式**：规则检查通过不等于 PowerPoint 里没问题。视觉验收必须用 PowerPoint 真实导出，由人看。

## 6. 方案

### 6.1 一页是怎么做出来的

```
已核对的页面内容 ──► 模型写这一页的 HTML ──► 浏览器排版并量尺寸
                                                    │
                          有问题就带着问题重写 ◄── 自动检查（溢出、重叠、字太小、多出数字）
                                                    │
                                              转成页面结构（PageDesign）
                                                    │
                                 现有渲染器输出 PPT ──► 截图给视觉模型看 ──► 有问题再改一轮
```

分两步写，是为了让核对发生在设计之前：

1. **内容步**：模型根据这一页拿到的原文片段，写出这一页要讲的结论、事实和数字，每条带出处。沿用现有的出处校验和数字核对（`evidence_check.py`、`typeset_pipeline.py` 里的 `repair_citation`、`check_content_numbers` 等）。内容的结构比现在宽松：不再绑定某一种构图，只描述「结论、若干事实块、可选的图表数据或表格数据」。
2. **设计步**：模型拿到已核对的内容和主题说明，写这一页的 HTML。只能使用主题提供的样式类和少量布局属性，不能写任意颜色和字号。
3. **设计后的核对**：页面上出现的每个数字都必须来自第 1 步已核对的内容。多出来的数字视为问题，退回重写。
4. **量尺寸与自动检查**：浏览器按 1280×720 排版。检查项：文字超出所在容器、元素超出页面、文字互相重叠、正文字号低于下限、页面留白过多或过满。发现问题时把具体问题发回模型重写，最多重试 2 次（Claude 的决定）。
5. **转换**：把量到的元素转成现有的 `PageDesign` 结构（`ir.py`），交给现有的 `render.py` 输出。这样预览、修订、已有测试都可以继续用。
6. **看图检查**：把浏览器里这一页的截图交给视觉模型检查「是否有一个明确的视觉重心、是否有明显的对齐或拥挤问题、图形是否在表达标题里的结论」。有问题改一轮。20 页以内每页都看；更长的稿子抽查，比例由实施时按费用定，但封面、章节页和所有图表页必须看（Claude 的决定）。
   - 运行时看的是浏览器截图，不是 PowerPoint 导出图（Claude 的决定）。原因：现在唯一的导出方式是 `scripts/pptx_snapshot.sh`，靠 AppleScript 打开 PowerPoint 窗口，只能在装了 Office 的 Mac 上跑，放不进 MCP 或 Web 后台。
   - 代价：看图检查发现不了转换造成的问题。这部分靠第 8 节的还原度验收（人工用 PowerPoint 导出对比）来保证。
   - 对外表述要准确：模型看的是「自己设计的页面的渲染图」，不是最终的 PPT 文件。
7. **兜底**：重试后仍不合格的页，退回旧排版引擎生成，并记录在运行结果里。一页失败不影响其他页。

### 6.2 HTML 能用什么

模型能写的东西是受限的，这样转换器才能保证还原：

- 文字、矩形、圆角矩形、圆、线、纯色、线性和径向渐变、透明度、单边边框。试验已经验证了这些。
- 图表用专门的标记声明类型和数据，转成原生图表（`ChartItem`），在浏览器里用同样数据画一个占位图用来量位置。
- 表格用标准 `<table>`，转成原生表格（`TableItem`）。
- 图片用 `<img>`，转成图片元素（`ImageItem`）。
- 不支持的写法（复杂阴影、混合模式、滤镜、CSS 动画、任意字体）在转换前就拒绝，并作为问题发回模型。

`PageDesign` 需要扩展，才能表示试验里用到的东西：一个文本框里多种样式的文字、直接指定的颜色、透明度、渐变停靠点、圆角大小、字距。具体字段留给实施者设计，要求是旧数据仍然能读。

### 6.3 主题

三套主题，每套是一份完整的设计规范，不是一组模板：

| 主题 | 气质 | 样张里的特征 |
|---|---|---|
| 杂志编辑 | 研究院年报、杂志专题 | 米白底、衬线大标题、黑加朱红、细线、大留白 |
| 深色科技 | 发布会、AI 产品官网 | 近黑底、蓝青光晕、渐变数字、半透明卡片 |
| 明亮现代 | 新一代 SaaS 品牌手册 | 暖白底、墨绿大色块、荧光黄绿点缀、大圆角 |

每套主题包含：颜色和字号变量、一组样式类、给模型看的设计说明（什么时候用大数字、什么时候用整页色块、留白怎么留）、若干页示范 HTML。样张在 `.superpowers/brainstorm/23141-1794271857/content/visual-directions.html`，可以直接作为示范页的起点。

- 字体改用 Office 自带字体后，三套主题要重新出样张给 Jay 看一次。「杂志编辑」依赖粗宋体，Office 自带的宋体没有真正的粗体，这一套可能要调整标题的做法，是已知风险。
- 旧的四种风格（consulting、launch、training、corporate）保留，只作为兜底引擎使用，不再改动（Claude 的决定）。
- 新流程验收通过后才改成默认。在此之前通过参数选择新旧流程。

### 6.4 配图

Jay 2026-11-10 确认：

- **第一阶段不接图片生成接口。** 页面的视觉靠三样可编辑的东西：数据本身做成图形（大数字、原生图表、用形状画的流程和对比）、图标（接入现有的 `icons.py`）、每套主题自带的抽象图形（渐变、光晕、几何色块）。
- **第二阶段再加图片生成，只用在封面和章节页，默认关闭。** 每套主题配一段固定的画面风格描述。平台到时再定，先看现有代理有没有开放图片接口。第二阶段不在本次范围内，接口留好即可。
- 不从资料 PDF 里截取图表当配图：截图里的数字核对不了，和第 4 节冲突。
- 内容页不配生成图。

### 6.5 长稿（40 页以上）

1. **先定论证线。** 大纲阶段写出整份稿子的主线：每个章节要证明什么，每一页在章节里承担什么。每页的内容步会拿到这条主线和相邻页的结论。
2. **事实台账。** 每个被使用的事实（数字加它说明的指标）记一笔。同一个事实最多做一次页面主角，最多再被引用两次（Claude 的决定）。内容步拿到「已经用过的事实」列表。
3. **页数建议。** 生成前估算资料能撑起多少页（按章节数和可用事实数）。用户要的页数明显超出时，MCP 的澄清环节要告诉用户并给出建议页数；用户坚持时照做，但台账规则不放松，撑不满的页数用联网资料补，仍不够就少做并说明。
4. **版式不重复。** 每页转换后算一个「版面特征」（主要区块的数量和排布）。设计步会拿到前几页的版面特征，要求不重复。
5. **仍然并发生成（Claude 的决定）。** 上面几条字面上要求按顺序写，但按每秒 35 token 顺序跑 100 页要几个小时。做法和现在的 `plan_archetypes` 一样：在大纲阶段就把事实和大致的版面类型分配到每一页，然后并发生成；全部完成后统计台账和版面特征，只重做有冲突的页。

### 6.6 接入

- CLI、Web、MCP 三个入口都能选新流程和三套主题。
- 修订单页（`revise_deck`）在新流程下的做法：带着修改意见重新走这一页的设计步，内容有变时先重新走内容步和核对。每页的 HTML 作为检查点保存。
- Web 预览要能显示新流程的页面。用现有的预览方式还是直接显示浏览器截图，留给实施者决定。
- 新增依赖：Playwright 和一个 Chromium 内核浏览器。没有浏览器时自动使用旧引擎并提示。

## 7. 建议的先后顺序

实施计划会细化，这里只给顺序和理由（Claude 的决定）：

1. **转换器做扎实**：字体、原生图表、表格、图片、`PageDesign` 扩展。字体是最大的风险，先解决。验收是手写样张转换后与浏览器截图一致。
2. **三套主题规范**，用 Office 字体重出样张，Jay 确认。
3. **单页生成流程**：内容步、设计步、自动检查、看图检查、兜底。用 20 页真实生成验收。
4. **长稿**：论证线、事实台账、页数建议、版面特征。用 100 页真实生成验收。
5. **接入** CLI、Web、MCP 和修订。
6. **评测与收尾**：盲评、记录、README、演示、简历。

第 3 步结束时就有一份可以给人看的 20 页成品。这时做一次小范围盲评（Claude 的决定）：Jay 自己加至少 3 个不知道来源的人排序。平均名次不是第一，就停下来和 Jay 重新商量，不继续做后面的步骤。第 8 节的正式盲评在第 6 步做。

## 8. 验收

| 项目 | 方法 | 标准 |
|---|---|---|
| 精美度 | 同一需求生成 20 页，与 Claude Code、Codex 各一份随机改名。Jay 找至少 5 个不知道来源的人排序 | ppt-agent 的平均名次最好。如实记录人数和每个人的排序 |
| 盲评口径（Claude 的决定） | 需求和对比稿沿用 `data/visual-upgrade/blind/` 里那一组（信通院报告，20 页）。只拿一套主题参评，由 Jay 选。评审看的是 Mac 上 PowerPoint 导出的 PDF | 另外两套主题不参加排序，但要通过本表其余各项 |
| 还原度 | PowerPoint 导出图与浏览器截图逐页对比 | 人眼看不出明显差别；元素位置偏差的自动指标由实施者定阈值 |
| 不溢出 | 20 页和 100 页真实生成，PowerPoint 导出后逐页看 | 0 处溢出或重叠 |
| 可编辑 | 脚本统计 | 没有用图片承载的文字；图表、表格全部是原生的 |
| 出处与数字 | 沿用现有核对 | 页面上的数字全部来自已核对内容；出处不合格 0 页 |
| 版式重复（100 页） | 版面特征统计 | 相邻 5 页内没有相同特征；任一特征占比不超过 8%（Claude 的决定） |
| 内容重复（100 页） | 事实台账统计 | 没有事实超过「一次主角加两次引用」；没有重复标题 |
| 兜底比例 | 运行记录 | 退回旧引擎的页不超过 5%（Claude 的决定） |
| 费用与时间 | 运行记录 | 如实记录，不设门槛。和现有 100 页的 4.3 分钟、约 5.5 美元对比 |
| 回归 | 全部现有测试 | 通过。旧引擎行为不变 |

## 9. 简历上可以写什么

- 定位：为什么宿主模型能做 PPT 之后这个项目还有价值，答案从「不编数字」变成「好看、有出处、可编辑」同时成立。

## 11. 已知风险

- **字体**：粗宋体可能做不出来，「杂志编辑」主题需要调整。
- **费用和时间上升**：每页从 1 次调用变成 2 到 4 次，加上看图。100 页的费用可能翻倍以上。
- **模型写 HTML 的稳定性**：Claude Code 那一版背后的模型更强，而这里设计步仍用 `gpt-5.6-terra`。代理模型在受限的写法下能否稳定产出好看的页面，要到第 3 步才知道。兜底引擎保证不会交不出稿，但兜底比例高就说明这条路对这个模型不合适。
- **盲评结果不可控**：做完之后仍可能排不到第一。届时如实记录。
